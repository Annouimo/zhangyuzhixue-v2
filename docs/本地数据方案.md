# 章鱼智学 · 本地数据方案

> 本文档定义数据的分类、存储策略、同步方案、API 设计原则、SharedPreferences 规范、网络请求失败处理、图片路由规范、同步队列重试策略以及更新机制。

---

## 一、本地数据方案

### 1.1 数据分类

| 类别 | 内容 | 来源 | 同步方式 |
|------|------|------|---------|
| 题库 | 题目、步骤、知识卡片 | App 预置 | 版本号检查 → 下载 .db 替换 |
| 元数据 | 课程、讲义、作业 | App 预置 | 同上 |
| 用户操作 | 提交记录、反馈、评分 | 本地写入 | 队列推送到服务器 |
| 组卷 | 学生自组试卷 | 本地写入 | 队列推送到服务器 |
| 积分 | 积分余额 | 服务器计算 | 本地缓存显示 |

### 1.2 预置题库数据库

- 开发时用 drift 建好全量表结构，导入数据生成 `.db` 文件
- 放入 Flutter `assets/` 目录
- App 首次启动复制到应用文档目录（`getApplicationDocumentsDirectory()`）
- 后续启动直接使用，无需等待网络

**更新流程（详见 [二、更新机制](#二更新机制)）：**
- App 启动时调用 `GET /api/sync/qbank/version`
- 响应包含 data_version、force_update、download_url、checksum 等字段
- 版本落后 → 按 force_update 策略决定提示方式
- 前台弹窗下载 .db 文件 → 校验 checksum → 整体替换

### 1.3 用户数据同步

**写入流程：**
```
用户操作 → 写入本地 SQLite（即时响应）
         → 追加 sync_queue 表
         → App 启动时/手动触发批量推送
```

**队列表结构：** `entity_type` / `operation_type` / `payload`(JSON) / `status` / `retry_count`

**冲突处理：** LWW（last-write-wins），服务器比较 `updated_at` 覆盖旧值。用户数据均为单人独写，不存在多用户写同一条记录的情况。

### 1.4 API 层设计说明

服务器（新版 Django）只提供两类接口：

| 接口类型 | 说明 |
|---------|------|
| **REST API** | Flutter 客户端调用（认证、数据同步、查询等） |
| **Django Admin** | 管理员后台（管理学生/班级/题目/数据查看） |

**核心原则：**
- 不提供面向学生/教师的网页端，仅通过 API 与 Flutter 客户端交互
- 数据字段映射仅在 API 层处理（serializer），不侵入业务逻辑
- 同步接口保持幂等（LWW 冲突解决）

### 1.5 SharedPreferences 路径规范

SharedPreferences 用于存储**纯客户端状态**，不经过 Repository 体系（不走数据同步流程）。

#### 使用场景汇总

| 场景 | key 命名 | 对应页面 | 说明 |
|------|---------|---------|------|
| 登录 access token | `app_auth_token` | auth, 全局 | JWT access token，登录成功后存储，登出时清除 |
| 登录 refresh token | `app_refresh_token` | auth, 全局 | JWT refresh token，用于无痛刷新 access token |
| 用户信息缓存 | `app_user_cache` | 全局 | JSON { id, name, role }，启动时快速路由（决定直接进首页还是跳登录页） |
| 评价弹窗冷却 | `solve_rating_cooldown_{page}` | solve-solve, paper_quicklook, lecture_content | 同页 24h 内不重复弹出 |
| 版本更新弹窗 | `app_update_last_shown` | 全局 | 上次提示版本更新的时间 |
| 解题防刷上次提交 | `solve_last_submit_{questionId}` | solve-choice/fill | 10s 冷却校验 |
| 新手引导标记 | `{page}_guide_done` | 各页面 | 首次进入新手引导 |
| 题库版本号 | `app_qbank_version` | 全局 | 当前 assets.db 的 data_version |
| 讲义版本号 | `app_lecture_version` | 全局 | 当前 lectures.db 的 data_version |

#### key 命名规范

```
{页面缩写}_{用途}
```

- 全局性的 key 以 `app_` 开头
- 页面级的 key 以页面缩写开头
- 需要区分具体对象的 key，在末尾拼唯一标识（如 `{questionId}`）

#### 代码规范

- 每个页面对应的 Dart 文件内声明 `_Prefs` 类，集中管理该页使用的所有 key
- 全局共用的 key 放在 `lib/constants/app_prefs.dart`

```dart
// pages/solve/solve_page.dart 头部
class _SolvePrefs {
  static const String lastSubmit = 'solve_last_submit_{qid}';
  static const String ratingCooldown = 'solve_rating_cooldown';
}
```

不设 HTML 标记，不在原型中标注。

### 1.6 网络请求失败处理

本 App 是本地优先架构，绝大多数数据从本地 SQLite 读取，网络请求仅限于少量场景：

| 请求类型 | 失败处理 |
|---------|---------|
| 登录/注册 | 必须在线，失败则表单上方显示红色内联错误提示 |
| 版本检查 | 静默失败，使用本地缓存的版本号，不提示用户 |
| 同步队列推送 | 保留在队列中，下次启动或手动触发时重试；同步队列页面已有错误提示 |
| 用户信息 / 偏好拉取 | 静默失败，使用 SharedPreferences 缓存的版本 |
| 下载 .db | 前台弹窗显示失败，用户可重试；下次启动自动重试 |

登录后 token 存本地 SharedPreferences，只要用户不退出登录即可正常使用全部核心功能（做题、组卷、统计等），无需重复网络请求。

### 1.7 图片路由规范

本规范定义 App 中两类图片（题库配图、用户头像）的存储位置、路径格式和解析规则。

#### 题库配图

图片来源：从源材料（PDF/Word 试卷）中提取的几何/函数示意图。构建脚本同步到 Flutter assets（客户端渲染）和 Django static/questions/images/（服务端 HTML 打印）两份。

**存储位置：**

```
assets/questions/images/
├── 一模/
│   ├── 2024/海淀/q17.webp
│   └── ...
├── 二模/
│   └── ...
└── 高考/
    └── ...
```

所有配图统一为 **WebP** 格式，由服务端 `convert_to_webp.py` 批量转码后打包到 App 中。

**Repository 模型中的引用：**

`QuestionDetail.images` 字段存储相对路径列表，不含 `/static/questions/附图/` 前缀：

```dart
images: ['一模/2024/海淀/q17.webp']
```

**解析方式：**

配图直接使用 `AssetImage` 加载。assets 中不存在即为 bug，不做网络回退。

**渲染位置：**

配图显示在题干下方。多张配图按 `images` 数组顺序纵向排列。Flutter 实现时用 `ImageResolver` 返回 `AssetImage`。

**后续待完成：**

| 事项 | 时机 | 说明 |
|------|------|------|
| 服务端 WebP 批量转码 | 新版 Django 上线前 | 已有 `convert_to_webp.py` 脚本 |
| 打包 `assets/questions/images/` 目录 | Flutter 构建时 | 在 `pubspec.yaml` 中声明 |
| 图片提取与存储：`images` 字段 | 数据入库阶段 | 从源材料提取 `<img>` 标签或图形，单独存放为 `images` JSON 字段，`stem` 中仅保留自然语言引用 |

#### 用户头像

**上传流程（不进同步队列）：**

```
用户选图 → resize 200×200 → 存本地文件系统
       → POST multipart/form-data → /api/user/avatar/
       → 服务端返回 URL
       → 更新本地 avatar 字段
```

头像不上传涉及的内容：**同步队列**（`SyncQueue`）设计用于 JSON 结构化数据的批量提交。头像是二进制文件，传 multipart/form-data 与传 JSON 的端点不同，混入队列需要 base64 编码（膨胀）且批量推送端点不支持 multipart。头像上传走独立接口，URL 作为用户信息随下次 `UserInfo` 同步推送。

**客户端渲染：**

优先展示本地缓存的版本，后台静默请求最新 URL。使用 `cached_network_image` 实现：首次加载时缓存到磁盘，后续离线时直接读取缓存。

**后续待完成：**

| 事项 | 时机 | 说明 |
|------|------|------|
| Django `Student.avatar ImageField` | 新版 API | 服务端存储 |
| 上传时 resize + WebP 压缩 | 新版 API | 限制体积 |
| Flutter 端上传 UI | Flutter profile_edit 开发时 | 复用原型已有逻辑 |

### 1.8 同步队列失败重试策略

#### 状态机

```
               入队
                 │
                 ▼
            ┌─────────┐
            │ pending  │
            └────┬────┘
                 │ pushAll() 开始处理
                 ▼
            ┌───────────┐
            │ inProgress │
            └─────┬─────┘
                  │ 请求返回
         ┌────────┼────────┐
         ▼        ▼        ▼
    ┌───────┐ ┌──────┐ ┌──────────────┐
    │ done  │ │failed│ │permanentFail │
    └───────┘ └──┬───┘ └──────────────┘
                 │ retryCount < maxRetries
                 │ → 下次 pushAll() 重新处理（见下文"孤儿记录"）
```

**约定：**
- `pending` — 待推送，每次 `pushAll()` 从 pending 和 inProgress 中取出
- `inProgress` — 正在推送中（防止同一记录被多个批次取出）。App 被杀导致的孤儿记录，下次启动时重新取出
- `done` — 推送成功，下次 cleanup 时删除
- `failed` — 推送失败，`retryCount < maxRetries` → 下次 `pushAll()` 取出重新推送
- `permanentFailure` — `retryCount >= maxRetries` → 不再推送，保留供用户查看

#### 重试策略

**最大重试次数：** 5 次。5 次足够覆盖短暂网络抖动，超出后转为 permanentFailure。

**退避策略：不做指数退避，仅 30 秒冷却检查。** 原因：所有重试触发均为人工操作（"全部重试"按钮 / App 启动），指数退避在手动触发场景下无意义。

```dart
// 冷却检查：距上次推送不足 30 秒则跳过（防连续点击按钮）
if (DateTime.now().difference(_lastPushTime).inSeconds < 30) return;
```

**触发时机：** 仅 App 启动和用户点击"全部重试"。不做后台定时器，不做网络恢复自动推送（省电省流量）。

#### 错误分类处理

| 错误类型 | 判定 | 处理 |
|---------|------|------|
| 网络错误（无网/超时/DNS） | DioException | `markFailed()`，retryCount+1，不中断队列 |
| 服务端 5xx | HTTP 500/502/503 | 同上 |
| 服务端 4xx 业务错误 | ApiException.code (40001-40399) | 直接 `permanentFailure`——数据格式/权限问题重试也无解 |
| LWW 冲突 | PushItemResult.status == 'conflict' | 视为成功（`markSuccess`） |
| Token 过期（401） | ApiClient 拦截器自行刷新 | 不进入此状态机 |
| 数据校验失败 | code = 40301 | 直接 `permanentFailure` |

#### 孤儿记录处理

`getPending()` 改为查 `status IN (pending, inProgress)`。App 在推送中途被杀时，`inProgress` 的记录在下次启动时重新取出推送。

#### permanentFailure 处理

- 保留 **7 天**，到期 cleanup() 自动删除
- sync_queue 页面中永久失败条目显示"清除"按钮（不可重试）
- 用户可联系管理员排查

#### cleanup 清理规则

每次 `pushAll()` 结束后执行：
- `done` → 立即删除
- `permanentFailure` → created_at 超过 7 天 → 删除
- `failed` + retryCount >= maxRetries → 转为 permanentFailure

## 二、更新机制

### 2.1 更新对象

三个独立数据库，各自追踪版本号，各自下载 .db 整体替换：

| 数据库 | 内容 | 权限过滤 | 更新频率 |
|--------|------|---------|---------|
| assets.db | 题目、步骤、知识卡片、概念标签 | 无（所有学生可见） | 低 |
| lectures.db | 课程、章节、讲义内容、作业 | UI层过滤 course_ids 白名单 | 高 |
| user.db | 用户数据 | — | 不更新 |

### 2.2 版本号体系

| 版本号 | 类型 | 定义位置 | 变更者 | 不匹配时 |
|--------|------|---------|-------|---------|
| schema_version | int | Flutter 代码硬编码 + DB 内部 _meta 表 | 开发者改表结构 | 强制去商店更新 App |
| data_version | int | SharedPreferences 缓存 + 服务端返回 | 管理员上传 .db 时标注 | 按 force_update 处理 |
| app_version | semver | Flutter 包版本 | 开发者发新版时 | 仅"关于"页展示 |

### 2.3 统一 API

```
GET /api/sync/{type}/version
  type: qbank | lecture

响应：
{
  "schema_version": 1,
  "data_version": 5,
  "force_update": true,
  "message": "新增2025年高考真题，修正3处解析错误",
  "download_url": "/static/db/{type}_v5.db.gz",
  "checksum": "sha256:...",
  "size_bytes": 4194304
}
```

### 2.4 启动流程

```
App 启动 → 进入首页（不阻塞主界面）
  ↓
读 SharedPreferences 缓存（app_qbank_version / app_lecture_version）
  ↓
并发调用两个 version 接口
  ↓
schema_version ≠ 本地？
  ├─ 是 → 弹框 "请去应用商店更新 App"
  └─ 否 → data_version > 本地缓存？
       ├─ force_update == true
       │   └─ 全屏弹窗 [立即更新]（不可关闭）
       │       点击 → 前台弹窗 + 进度条 + "请不要退出"
       │       完成 → 验证 checksum → 替换 .db → 重启到首页
       │       失败 → 下次启动重试
       └─ force_update == false
            └─ 右下角横幅 5s [更新] [稍后]
                或 本地落后 ≥ 3 个版本 → 转为强制
```

### 2.5 更新窗口规则

#### 强制更新（满足任一即强制）

1. 管理员上传时标注 `force_update: true`
2. 本地版本落后服务端 ≥ 3 个版本
3. `schema_version` 不匹配

#### 非强制更新

- 每次启动展示右下角横幅，5s 后自动消失
- 用户可点击「稍后」关闭
- 不限制跳过次数

#### 下载中操作规范

- 前台弹窗 + 进度条，提示"请不要退出此页面"
- 不阻塞用户操作，但替换前不触发数据库读取
- 完成验证后关闭旧 Drift 连接 → 覆盖文件 → 重新打开 → 恢复界面

### 2.6 与同步队列的关系

更新机制与同步队列同属通信层面，但方向相反：

```
┌────────────────────────────────────────────┐
│        通信层面（Client ↔ Server）           │
│                                            │
│  ┌─────────────┐     ┌──────────────────┐  │
│  │  更新机制     │     │  同步队列          │  │
│  │  Server→Client │     │  Client→Server   │  │
│  │  .db 整体下发  │     │  用户操作批量推送   │  │
│  └─────────────┘     └──────────────────┘  │
│                                            │
│  共同基础设施：                              │
│  - 同一套 API 认证                           │
│  - 统一由 SyncManager 协调启动时序            │
│  - 网络失败处理策略一致                       │
└────────────────────────────────────────────┘
```
