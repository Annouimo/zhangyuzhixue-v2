> 本文档定义新版 Django 服务端（纯 API + Admin）的架构设计、App 划分、模型映射、认证方案、审计策略与部署策略。

> **状态**：设计阶段，未落地。

## 一、定位

| 维度 | 定位 |
|------|------|
| 角色 | 纯 API 后端 + Django Admin 管理端 |
| 客户端 | Flutter App（学生端 + 未来教师端）|
| 不做 | 网页前端（学生端/教师端均无 Web 界面）|
| 部署 | 单一 Django 进程 + gunicorn + nginx + Cloudflare Tunnel |

**核心原则：** 服务端只做三件事——认证鉴权、数据接收与持久化、管理员操作入口。

### 3.5 `system` — 系统管理

| 模型 | 说明 |
|------|------|
| `DbVersion` | 题库/讲义版本号记录，管理端编辑 |

#### DbVersion 模型

版本号记录表，独立 App 避免归属争议（同时管理 qbank 和 lecture 两类版本）。

```python
class DbVersion(models.Model):
    DB_TYPE_CHOICES = [
        ('qbank', '题库'),
        ('lecture', '讲义'),
    ]
    db_type = CharField(max_length=20, unique=True, choices=DB_TYPE_CHOICES)
    schema_version = IntegerField(default=1)
    data_version = IntegerField(default=1)
    force_update = BooleanField(default=False)
    message = TextField(blank=True)          # 更新日志
    checksum = CharField(max_length=128)     # SHA-256
    size_bytes = IntegerField(default=0)
    download_url = CharField(max_length=500) # 如 /media/db/qbank_v5.db.gz
    created_at = DateTimeField(auto_now_add=True)
    updated_at = DateTimeField(auto_now=True)
```

**数据流：**

```
管理员上传新版 .db.gz → 在 Django Admin 中录入版本号/checksum/message
                      → 保存 DbVersion 记录
                      → API GET /api/v1/sync/qbank/version/ 直接查此行返回
```

`DbVersion` 表同时服务两个数据源（题库 + 讲义），每类一条记录，通过 `db_type` 区分。

## 五、数据库选型

### 决策：SQLite (WAL)

| 维度 | 选型 |
|------|------|
| 引擎 | SQLite 3 |
| 模式 | WAL（Write-Ahead Logging）|
| 配置 | `timeout=20`，`transaction_mode='IMMEDIATE'` |
| 启用 | Django signal `connection_created` 执行 `PRAGMA journal_mode=WAL;` |

沿用旧版的 SQLite 配置已验证可行。当前用户规模极小（~3 教师 + 数十学生），服务端写入为低频批量推送，SQLite 的串行写不构成瓶颈，运维成本为零。

## 九、审计日志策略

### 9.1 方案

引入 `django-auditlog`，零侵入自动记录：操作人、操作时间、操作类型（CREATE/UPDATE/DELETE）、变更字段的 JSON Diff、操作对象 ID 及模型名称。

### 9.2 审计范围

模型按以下三类区分：

**默认审计（注册 auditlog）：**

| 模型 | App | 理由 |
|------|-----|------|
| `BaseQuestion` / `ChoiceExt` / `SubQuestion` / `SolutionMethod` / `SolutionStep` | qbank | 题库是核心资产，改错能溯源 |
| `KnowledgeCard` / `ConceptTag` | qbank | 同上 |
| `Document` | courses | 讲义内容，需要版本追溯 |
| `Course` / `ClassGroup` / `ClassCourse` | courses | 班级课程体系，结构变动需记录 |
| `Assignment` / `AssignmentQuestion` / `ClassCourseAssignment` | courses | 作业发布/修改，教师操作需追溯 |
| `Student` / `Teacher` / `User` | accounts | 用户身份管理 |
| `DbVersion` | system | 版本发布记录 |
| `InvitationCode` | accounts | 邀请码谁创建、谁使用 |

**不应审计：**

| 模型 | 理由 |
|------|------|
| `StudentSubmission` / `SubmissionDetail` / `StepFeedback` / `CardFeedback` | 量太大。每个学生每次做题都产生，日志会爆炸。这是学习行为数据不是管理操作，无审计价值 |
| `QuestionRating` | 同上，学生个人评分行为 |
| `CustomPaper` / `CustomPaperQuestion` / `PaperLike` / `PaperCollect` | 学生个人行为，无管理审计意义 |
| `UserLoginLog` | 本身就是日志，再审计就套娃了 |
| `PageSatisfactionFeedback` | 纯问卷数据，无审计价值 |

**条件审计：**

| 模型 | 方案 |
|------|------|
| `PointsTransaction` | 注册 auditlog，但只关注 `ADMIN_ADJUST` 类型。由于手动调整积分的操作极少（一年十几次），全量注册不影响 |

## 十、构建脚本

> 详见 [构建脚本设计.md](构建脚本设计.md)。

从 Django 数据构建客户端 assets.db 和 lectures.db 的构建脚本，采用**独立 drift schema 定义**方案——在脚本中维护一套独立的资产库表结构定义和字段映射逻辑，而非从 Django models 自动推导。理由：

- 客户端资产库有独有表（`chapter`），服务端无对应模型
- 客户端与服务端字段类型不同且不需要一一对应
- 独立定义比隐式推导更安全可控

## 十一、Admin 与操作入口

### 11.1 默认 Admin 注册策略

所有需要管理的模型统一注册到 Django Admin。注册方式为每模型一行 `@admin.register` + 视情况定制：

```python
# 示例：各 App 的 admin.py

# accounts/admin.py
@admin.register(User)
class UserAdmin(admin.ModelAdmin):
    pass  # 默认 CRUD，后续按需定制

@admin.register(Student)
class StudentAdmin(admin.ModelAdmin):
    pass

# qbank/admin.py
@admin.register(BaseQuestion)
class BaseQuestionAdmin(admin.ModelAdmin):
    pass  # 后续加 Inline 展示 SubQuestion / SolutionMethod / SolutionStep
```

Django 自动生成的 CRUD 界面（列表/搜索/详情/编辑）对所有模型已足够使用，定制化改造**非开工必要**，逐步进行。

### 11.2 两种操作类型

Django Admin 内的操作分为两类，各有各的入口方式：

### 🛠 系统级操作 — `/admin/system/tools/`

这些操作不依赖具体某条数据库记录，作用于系统整体。放在 `system` App 下一个**自定义 Admin 视图页面**中，以按钮/卡片形式列出：

| 操作 | 说明 |
|------|------|
| 构建并发布 · 题库 | 构建 assets.db → gzip 压缩 → 更新 DbVersion（checksum/size/download_url/data_version）|
| 构建并发布 · 讲义 | 同上，构建 lectures.db |
| 仅构建测试 · 题库 | 只生成 .db.gz 文件，不更新版本号（用于开发验证）|
| 仅构建测试 · 讲义 | 同上 |
| 批量生成邀请码 | 输入数量 → 生成 N 个随机邀请码（格式 `XXXX-XXXX-XXXX`）|
| 导出未使用邀请码 CSV | 导出全部未使用的邀请码列表 |
| 批量导入学生 | 上传 CSV（姓名/学号/班级）→ 创建 User + Student + 分配班级 |

底层调用与 `manage.py` 命令相同的函数，Admin 仅是操作入口，命令行也可执行。

### 📋 模型级操作 — 对应 ModelAdmin `actions` 下拉

这些操作需要选中一条或多条记录：

| App | 模型 | 操作 | 说明 |
|-----|------|------|------|
| `accounts` | `PointsTransaction` | 管理员手动调整积分 | 选学生 → 输入金额 → 创建 ADMIN_ADJUST 记录 |
| `qbank` | `BaseQuestion` | 批量导出 JSON | 导出选中题目的完整数据（含关联子表）|
| `qbank` | `BaseQuestion` | 批量导入 JSON | 导入题目（含 stem/images/sub_question/solution）|
| `qbank` | `BaseQuestion` | 图片重提取 | 选中题目 → 从 stem 提取 `<img>` 到 images 字段 |
| `courses` | `ClassGroup` | 批量导入学生 | 选班级 → 上传 CSV → 导入学生 |
| `courses` | `Document` | 讲义预览 | 选中一篇讲义 → 预览 LaTeX 渲染效果（P3 暂缓）|

### 不需要自定义操作的模型

以下模型 Django 默认 CRUD 已足够，无需定制任何 action：

| App | 模型 | 说明 |
|-----|------|------|
| `accounts` | User / Student / Teacher | Student 编辑班级关联用默认下拉选足够 |
| `qbank` | ChoiceExt / SubQuestion / SolutionMethod / SolutionStep | 建议用 Inline 内嵌在 BaseQuestion 编辑页，但不是 action |
| `qbank` | ConceptTag / KnowledgeCard | 默认 CRUD + 树形展示（`list_display` 定制，不是 action）|
| `courses` | Course / ClassCourse / ClassCourseAssignment | 默认 CRUD |
| `courses` | Assignment / AssignmentQuestion | 查看为主（教师端 Flutter 发布作业）|
| `interactions` | 全部 | 查看为主，默认 CRUD |
| `system` | DbVersion | 默认 CRUD（版本号编辑）|
