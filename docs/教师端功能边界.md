# 章鱼智学 · 教师端功能边界

> 本文档定义教师端的角色定位、职责边界、页面清单、数据流与 API 需求，
> 以及与 Django Admin 端的职责划分。
> 学生端完工后，在此文档基础上进一步设计交互细节与开发实现。

---

## 一、角色定位

| 维度 | 定位 |
|------|------|
| 用户 | 教学工作从事者（当前约 3 人，长期不会大幅增长） |
| 客户端 | Flutter 软件（未来开发），无网页端 |
| 核心任务 | 选题发布作业 + 查看学生完成情况 |
| 数据范围 | 可见全部班级和全部学生，不做权限隔离 |
| 与内容的关系 | 只消费内容（题库/讲义），不编辑内容 |

**核心原则：** 教师「选人、选题、发布、看结果」，不做内容编辑。

---

## 二、职责边界

### 2.1 教师能做的

| 功能 | 说明 |
|------|------|
| 浏览题库并选题 | 复用学生端的筛选面板，从现有题库中勾选题目 |
| 发布作业到班级 | 组合题目 → 设标题/截止日期 → 发布到目标班级 |
| 查看作业完成情况 | 每个学生是否已做、正确率、提交详情 |
| 查看班级整体学情 | 班级平均正确率、完成率、各题型表现 |
| 查看学生个人报告 | 做题量、正确率趋势、薄弱知识点 |
| 发送催交通知 | 对未交学生发送提醒（未来扩展） |
| 查看讲义 | 与学生端相同的讲义阅读体验 |
| 编辑个人资料 | 姓名、头像等 |

### 2.2 教师不能做的

| 功能 | 原因 | 替代方案 |
|------|------|---------|
| 编辑题目（题干/答案/解析/难度等） | 题库为平台统一资产，多人编辑易不一致 | 联系管理员在 Django Admin 修改 |
| 创建新题目 | 同上 | 联系管理员录入 |
| 编辑讲义内容 | 讲义 Markdown 为平台统一维护 | 通知管理员通过 Django Admin 更新 |
| 管理班级信息（增删班级） | 班级结构由管理员维护 | 联系管理员 |
| 管理学生账号 | 学生账号由管理员/系统导入 | 联系管理员 |
| 调整学生积分 | 仅管理员可手动调整 | 联系管理员 |
| 修改系统配置（版本号、公告等） | 运维权限 | 仅管理员可操作 |

### 2.3 讲义编辑的实操方案

教师使用 **Obsidian** 编写讲义 Markdown 文件（含 LaTeX 公式、分隔符 `<!-- pagebreak -->` 和 `<!-- reveal -->`），编写完成后复制粘贴到 Django Admin 的讲义编辑页面中保存。

**注意：** Django Admin 的 textarea 当前不渲染 LaTeX 公式，保存后需要在学生端 App 中查看实际渲染效果。未来可考虑在 Admin 页面增加预览功能（低优先级）。

## 四、数据流与 API

### 4.1 整体数据流

```
┌────────────────────────────────────────────────────────────┐
│  教师 Flutter App                                             │
│                                                              │
│  ┌───────────┐  ┌───────────┐  ┌──────────────────────────┐ │
│  │ UI 层      │  │ Repository │  │ 本地缓存                   │ │
│  │ (Widget)   │◀─│ (拼装数据)  │◀─│ ├─ 题库 assets.db（只读）│ │
│  └───────────┘  └───────────┘  │ ├─ 讲义 lectures.db（只读）│ │
│                                 │ └─ SharedPreferences       │ │
│                                 │       │                   │ │
│                                 │   POST/PUT → API          │ │
│                                 │   (教师操作不走 sync_queue) │ │
│                                 └───────────┬──────────────┘ │
└─────────────────────────────────────────────┼────────────────┘
                                               │ HTTPS
┌──────────────────────────────────────────────┼─────────────────┐
│  服务器 (Django)                               │                 │
│                                               ▼                 │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │  REST API（教师专属端点 + 共用端点）                        │ │
│  │  ├─ /api/teacher/assignments/  — 作业发布/列表/详情        │ │
│  │  ├─ /api/teacher/classes/      — 班级列表（含统计）        │ │
│  │  ├─ /api/teacher/students/     — 学生列表/详情            │ │
│  │  ├─ /api/teacher/assignments/{id}/remind/  — 催交        │ │
│  │  └─ 共用端点：/api/auth/、/api/sync/* 等                 │ │
│  └────────────────────────────────────────────────────────────┘ │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │  Django Admin  （管理员管理端）                             │ │
│  │  题库/讲义/用户/版本/审计 管理                              │ │
│  └────────────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────┘
```

### 4.2 教师专属 API 端点

| 方法 | 端点 | 说明 |
|------|------|------|
| `GET` | `/api/teacher/assignments/` | 作业列表（含完成率等统计信息） |
| `POST` | `/api/teacher/assignments/` | 创建并发布作业（含题目列表、班级列表、截止日期） |
| `GET` | `/api/teacher/assignments/{id}/` | 作业详情（按学生列出完成状态） |
| `DELETE` | `/api/teacher/assignments/{id}/` | 撤销/删除作业 |
| `PATCH` | `/api/teacher/assignments/{id}/` | 修改截止日期等 |
| `GET` | `/api/teacher/classes/` | 班级列表（含学生人数、平均正确率等概览统计） |
| `GET` | `/api/teacher/students/` | 学生列表（可搜索/筛选，含关键指标） |
| `GET` | `/api/teacher/students/{id}/` | 学生详情（做题历史、正确率趋势、薄弱知识点） |
| `POST` | `/api/teacher/assignments/{id}/remind/` | 催交（推送通知给未交学生，未来实现） |

**关于同步机制：** 教师端的写操作（发布作业等）**不走 sync_queue**（sync_queue 是学生端本地优先的异步推送设计）。教师端是直接在线操作，调用 API 即时写回服务器，失败则显示错误提示让用户重试。

### 4.3 教师端与学生端共用的端点

| 端点 | 说明 |
|------|------|
| `/api/auth/*` | 登录/注册/Token 刷新 |
| `/api/sync/qbank/version` | 题库版本检查 |
| `/api/sync/lecture/version` | 讲义版本检查 |

## 五、认证与角色校验

### 5.1 角色体系

系统共有三种角色，由服务端统一管理：

| 角色 | 登录端 | 账号创建方式 |
|------|--------|-------------|
| `student` | 学生 Flutter App | 自助注册（需邀请码） |
| `teacher` | 教师 Flutter App（未来） | 管理员在 Django Admin 手动创建 |
| `admin` | Django Admin 内置登录 | 管理员创建 |

### 5.2 认证方案

采用 **JWT (djangorestframework-simplejwt)** 方案：

| 组件 | 方案 |
|------|------|
| Token 格式 | Access Token + Refresh Token |
| Access Token 有效期 | 24 小时 |
| Refresh Token 有效期 | 30 天 |
| 存储位置 | SharedPreferences（不引入 flutter_secure_storage；本 App 数据风险等级低） |
| 刷新端点 | `POST /api/auth/refresh/` |

### 5.3 登录校验流程

所有 Flutter App 共用同一个登录端点，通过 `app_type` 参数区分来源：

```
POST /api/auth/login/
{
  "username": "...",
  "password": "***",
  "app_type": "student"   // 或 "teacher"
}
```

服务端校验逻辑：

1. 用户名密码验证
2. 查询用户角色（关联 Student / Teacher / 均为空则为 admin）
3. 角色校验：

| 请求 `app_type` | 允许的角色 |
|-----------------|-----------|
| `student` | `student` |
| `teacher` | `teacher` |
| 其他值 | 均拒绝 |

> **管理员不登录 Flutter App。** 管理员如需验证 App 功能，使用专用的测试学生/教师账号。Django Admin 本身有独立的 session auth 登录。

4. 校验通过 → 生成 JWT pair + 返回用户信息

**响应格式：**

```json
{
  "access": "eyJhbG...NiIs...",
  "refresh": "eyJhbG...NiIs...",
  "user": {
    "id": 1,
    "name": "张三",
    "role": "student"
  }
}
```

### 5.4 启动时自动恢复登录

```
App 启动 → 读 SharedPreferences
  ├── access token 存在且未过期（本地解析 JWT 的 exp 字段）
  │   └── 直接进首页（快速路由，服务端会在正经请求时验证）
  ├── access 过期但 refresh 存在
  │   └── POST /api/auth/refresh/ → 新 access → 进首页
  └── 都无或都过期 → 进登录页
```

### 5.5 注册（仅限学生）

```
POST /api/auth/register/
{
  "invitation_code": "GR7X-K2P9-M4VB",
  "username": "zhangsan",
  "real_name": "张三",
  "phone": "13800138000",
  "gaokao_year": "2026",
  "password": "***"
}
→ 201: { "message": "注册成功，请登录" }
```

- 注册**不直接返回 token**，成功后跳转登录页
- 教师账号由管理员在 Django Admin 手动创建

### 5.6 登出

客户端操作：清除 SharedPreferences 中的 `app_auth_token`、`app_refresh_token`、`app_user_cache`。服务端无额外操作（JWT 无状态）。

### 5.7 密码找回

当前规模下不做自助找回。联系管理员通过 Django Admin 重置密码即可。

## 六、需要新增的服务端模型

### 6.1 `Teacher` — 教师身份（最小模型）

仅作为身份标记，不绑定班级（当前 3 人规模，可见所有班级）。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | AutoField | PK | |
| `user` | OneToOneField → User | NOT NULL, UNIQUE | Django 内置用户 |
| `name` | CharField | NOT NULL | 显示名称 |
| `created_at` | DateTimeField | auto_now_add | |

**为什么需要 Teacher 模型：**
- API 权限鉴别：区分「教师请求」和「学生请求」
- Django Admin 中识别管理员和教师
- 后续扩展时容易加字段

**实现建议：** `is_teacher` 字段可以直接放在 Django User 的 `user_permissions` 或 `groups` 中，但独立的 `Teacher` 模型更清晰，且方便后续加教师专属字段。

### 6.2 不需要新增的表

| 表 | 不需要的理由 |
|----|------------|
| `TeacherClassGroup` | 教师可见所有班级，无需中间表 |
| `TeacherCourse` | 同上 |
| `ClassGroupAssignment` （独立表） | 直接使用现有的 `ClassCourseAssignment` + `Assignment`，教师发布的作业也写入同一套表 |

## 八、教师端本地数据策略

教师端 Flutter App 使用本地数据的策略与学生端不同：

| 数据类型 | 策略 | 原因 |
|---------|------|------|
| 题库（assets.db） | 同学生端，整体下载替换 | 选题时需要离线浏览题目 |
| 讲义（lectures.db） | 同学生端 | 阅读讲义需要离线可用 |
| 教师操作数据 | 纯在线，不本地持久化 | 教师操作需实时生效，不依赖离线 |
| 班级/学生数据 | API 实时拉取，可简单缓存 | 数据实时性要求高（学生刚交的作业应立刻反映） |

教师端 **不需要** sync_queue 同步队列机制。
