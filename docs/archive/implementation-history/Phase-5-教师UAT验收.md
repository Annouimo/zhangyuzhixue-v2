## 第一步：准备工作（验收开始前）

### 1.1 教师账号清单

| 教师 | 用户名 | 密码 | 角色 |
|:-----|:-------|:-----|:-----|
| 教师 A | teacher_uat_a | 由项目负责人创建 | student（以学生身份） |
| 教师 B | teacher_uat_b | 由项目负责人创建 | student |
| 教师 C | teacher_uat_c | 由项目负责人创建 | student |

各账号须预注册完成（邀请码已使用、Student 表有记录）。每人登录后能看到同样的初始化首页。

### 1.2 设备要求

- 每人一台 Android/iOS 设备（或模拟器）
- 安装当前 staging 版本 Flutter App（或调研阶段先用浏览器 + responsive 模式看 Flutter Web build）
- 网络正常（可访问 `zhangyuzhixue.top`）

### 1.3 分批安排

建议分 2 批，不做大组一起：

| 批次 | 教师 | 时间 | 侧重点 |
|:-----|:-----|:-----|:-------|
| 第 1 批 | A + B | 第 1 天上午（2h） | 解题模式 + 讲义 + 评价弹层（最核心流程，发现问题最多） |
| 第 2 批 | A + B + C | 第 1 天下午或第 2 天 | 组卷 + 作业 + 推荐 + 统计 + 个人中心（含成就/积分学情） + 同步队列 + 首次引导 |
| 反馈修复 | — | 第 2–3 天 | 修 Bug → 部署 → 通知复测 |
| 复测签收 | A + B + C | 最终签收（~1h） | 确认反馈已修复 |

### 2.2 解题模式（选填题）

| 步骤 | 操作 | 预期结果 | 通过？ |
|:-----|:-----|:---------|:------:|
| 1 | 从首页或组卷进入一道选择题 | 题目题干显示（含 LaTeX 公式渲染）、选项可点、冷却倒计时开始（10s） | ⬜ |

## 第三步：问题分级与处理

验收过程中发现的问题按以下分级处理：

### 严重度定义

| 等级 | 标记 | 定义 | 举例 | 是否阻塞放行 |
|:-----|:-----|:-----|:-----|:------------|
| **S0 — 崩溃** | 🔴 | App crash、白屏、操作无响应 | 点击提交按钮闪退、登录后白屏 | **是** |
| **S1 — 数据错误** | 🔴 | 答案不对、题目数据遗漏 | 选择题判对错反了、配图不显示、成就计数错误 | **是** |
| **S2 — 功能缺失** | 🟡 | 某个交互序列走不通 | 冷却按钮始终禁用、翻页按钮无反应、引导弹窗消失后不显示表单 | **是** |
| **S3 — 体验问题** | 🟡 | 设计偏离但不阻塞 | 倒计时文字太小看不清、反馈文案不够清晰 | **建议改** |
| **S4 — 细节瑕疵** | ⚪ | 文案/样式/微调 | 颜色偏移 1px、页面标题不一致 | **后续改** |

### 处理流程

```
教师发现一个问题
    ↓
项目负责人记录（格式见下方模板）
    ↓
判断严重度
    ├── S0/S1/S2 → 立即排期修复 → 修复后部署 → 通知复测
    └── S3/S4   → 记录到 backlog → 集中一批修复（每轮 UAT 迭代末尾处理）
    ↓
┌── 本轮所有 S0/S1/S2 已修复？──┐
│  是                         否│
│                              ↓
│                         继续下一个迭代
↓
进入下一批验收或签收
```

### 反馈记录模板

每条反馈按以下格式记录：

```
---
ID: UAT-001
发现者: 教师 A
严重度: S2
功能: 解题模式-选择题
描述: 点击提交后，按钮变灰但结果区未显示，等待 5 秒后才出现
设备: iPhone 14 / iOS 17
截图/录屏: [链接]
状态: ✅ 已修复 / ⬜ 待修复
---
```

建议在验收期间开一个共享文档（飞书/腾讯文档），由项目负责人现场录入，教师可实时看到自己报的问题进度。

## 第四步：签收条件

当以下条件全部满足时，教师签字放行，进入 Phase 6：

1. **无未解决的 S0/S1/S2 问题** — 所有崩溃、数据错误、功能阻断已修复并通过复测
2. **11 个功能模块的全部脚本步骤** — 3 位教师均已走通一遍（通过率 ≥ 90%，未通过的为 S3/S4）
3. **至少 1 位教师完成解题数据核对** — 新旧版答案一致
4. **每位教师各签一个字** — 不要求三联单，口头或群里回复「可用」也行

### 签收格式

```
教师 A（签名/昵称）：________    日期：________   结论：✅ 可用 / ❌ 不可用
教师 B（签名/昵称）：________    日期：________   结论：✅ 可用 / ❌ 不可用
教师 C（签名/昵称）：________    日期：________   结论：✅ 可用 / ❌ 不可用

项目负责人确认：________    日期：________
```

## 第五步：验收后

签收后：
- Phase 3 + Phase 4 代码冻结（该阶段不再加新功能）
- 进入 Phase 6 用户迁移 + 上线
- 未修复的 S3/S4 问题进入 backlog，在 Phase 6 迭代中穿插修复
- UAT 期间发现的 S0/S1 问题若触发了代码改动，补对应的 Widget 测试（如果之前没有覆盖到）

## 注意事项

- **验收用的 staging 环境不要和开发环境打架。** 如果 Phase 6 已经并行推进，部署时注意分支隔离
- **不要用生产数据。** 教师试玩产生的 submission/feedback 数据全是测试数据，Phase 6 上线时不会迁移
- **教师不是 QA。** 他们的任务是「作为真实用户觉得好用吗」，不是「找所有 bug」。项目负责人同时在场观察操作卡点
- **旧版数据核对只核对答案正确性**，不核对 UI 像素级一致——新版是 Flutter 原生，不是 Web 的响应式 HTML
- **允许教师之间互相讨论。** 一个教师发现的问题，其他教师可能也会遇到，也能验证修复
