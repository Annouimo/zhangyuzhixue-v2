### 存档设计结论

存档机制的核心映射：**存档（Attempt）= submission_detail 表中同一 question_id 下由 attempt_number 区分的一条记录**。不新增独立表。`sub_question` 回归纯结构定义角色。详见 `docs/02-数据/数据库结构设计.md §6.2 submission_detail`。

### 有风险的点（需编码时关注）

1. **推荐算法冷启动**：5 题阈值可能导致做题 5 题后仍无推荐数据的边界情况
2. **组卷积分消耗**：扣分规则（一次组卷扣多少）未定义，需编码前确定
3. **SharedPreferences 数据量**：学生可访问的 course_ids 列表可能较长

### 不需要单独做的（规范已覆盖）

- 路由参数文档：Flutter代码规范.md §2.5 已定义 query param 约定，mode 由 ProgressRepository 运行时推算
- Prefs key 清单：规范已定义 `_Prefs` 前缀规则，编码时按需添加
- 推荐算法参数：完整参数在 测试策略.md 推荐算法测试用例中
- 启动时序：更新机制.md 伪代码 + 架构概览.md 数据流图已足够

## 三、建议的启动顺序

1. **服务端（server/）**：Phase 0-B + Phase 1（1.1~1.5）优先启动
2. **Flutter 数据层（lib/data/）**：Phase 0-A + Phase 2（2.1~2.4），与服务端并行
3. **Flutter UI**（Phase 3）：数据层就绪后从 3a→3b→3c 推进

最快可得的成果（1-2 天内）：Django 认证 API 调通 + Flutter 登录注册页面跑通。
