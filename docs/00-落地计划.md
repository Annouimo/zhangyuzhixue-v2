## 二、工作流原则

### 线性化

服务端 → Flutter 数据层 → Flutter UI → 辅助系统 → 集成测试 → 用户迁移上线，不并行。

**理由：** 服务端是数据源头（Django models → Drift 镜像；API → sync engine），Flutter 数据层需要服务端的接口契约就绪后才能对接。

### 每步测试

测试嵌入到每个子步骤中，不攒到最后集中做。理由：

- 测试用例已在 测试策略.md 中设计好（L1 算法单元 7 个私有类 × 每条用例 + L2 DAO 11 个 × 每条用例 + L3 Repository 13 个 + L4 同步引擎 30+ 场景），编码时直接"抄作业"
- 架构天然支持测试（构造注入 + memory DB，独立构造独立销毁）
- 最后测意味着 10+ 天积累的 bug 排查成本指数增长

**约定：** L1-L4 嵌入 Phase 1/2 的每一步；L5 Widget 测试嵌入 Phase 3 的每一步。仅 L6-L8（服务端契约/E2E/构建）留到最后的 Phase 5 集中做。

**1.2 题库迁移详细步骤：**

```
migrate_questions.py
├── 连接旧版 db.sqlite3
├── 迁移 ConceptTag（板块·概念树形结构）
├── 迁移 KnowledgeCard
├── 迁移 Question
│   ├── year/exam/district/number → new fields
│   ├── difficulty ×2（旧 1-5 → 新 0-10）
│   ├── workload ×2（旧 1-5 → 新 0-10）
│   ├── 从 question_text 提取 <img> 至 images JSON
│   └── 清理 stem（删除 <img> 标签）
├── 从 QuestionStep 构建 SubQuestion → SolutionMethod → SolutionStep（三层嵌套）
│   ├── subquestion=0 → index=0（选填题）
│   ├── method=0 → method_name=null（唯一解法）
│   └── group by (question_id, subquestion, method) → 逐层创建
├── 建立 question_knowledge_card M2M（从 card_refs 反向解析）
├── 复制 ./data/附图/ → static/questions/images/
└── 验证：题数 N→N、随机抽 5 题逐字段对比
```

**注意：** `difficulty` 旧版 Question 存 1-5，但旧版 QuestionRating 用的是 0-10。迁移以旧版 Question 数据为准，×2 映射到新版 0-10 连续值。

**用户数据本次不迁移**——开发阶段用 `createsuperuser` + 注册 API 创建测试用户即可。旧版用户数据留到 Phase 6 上线前统一迁移。
