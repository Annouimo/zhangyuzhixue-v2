# 章鱼智学 · 审查流程手册

> 本文档定义项目 Owner 验收审计的完整流程、审计分类、力度要求和常见陷阱。
> 审计由 Hermes agent 执行，加载 skill `project-owner-acceptance` 后按此手册操作。

---

## 一、核心理念

每次审查的目的是：**在确认当前交付质量是否达到 Owner 的可接受标准。**

**审计是对话产物——只报告，不修改。** Agent 发现的问题呈现给 Owner 判断，不经指示不修代码、不改文档、不跑数据迁移。

## 三、审查三步骤

### 第 0 步：读设计文档 → 提取陈述清单

1. 按审计类型（A-G）查上表，确定该读哪些文档
2. 批量读取全部文档
3. 输出清单，每项标注来源文档编号（如 `C4: exam_auto.html §筛选区 — 5 段筛选面板`）

### 第 1 步：拿清单对比计划

| 清单项 | 计划预期 | 结论 |
|--------|---------|------|
| ✅ 计划说已完成 | → 标记为"待代码验证" |
| ⬜ 计划说未开始 | → 标记为"延期" |
| ❌ 计划与设计矛盾 | → 标记为"计划-设计不一致" |

### 第 2 步：拿清单对比代码

分四个阶段执行：

**Phase A — 组件探针：** 每个类/方法/文件/路由存在吗？签名正确吗？（快速扫描，不深入）

**Phase B — 数据流追踪（强制 R2）：** 对设计文档描述的每个流程，追踪每步输出→输入的消费链。

```
Source → Step1 → Step2 → Step3 → Sink

在每个箭头处检查：
  └─ {上一步} 的输出被 {下一步} 捕获了吗？
  └─ 返回值赋值了吗？(var x = f() vs f())
  └─ 数据类型在定义文件之外被引用了吗？
  └─ 有 UI 组件或持久化层消费它吗？
```

**Phase C — 深度探测（强制 R1/R3/R4）：** 对 Phase A 发现的每个组件，按各类型的 layer-specific probes 表做深度检查。

**Phase D — UI vs HTML 原型比对（仅 Type C）：** 打开 HTML 原型 → 提取 UI 元素清单 → 打开 Flutter Widget → 逐项比对布局/文字/绑定/交互/空态。

## 四、力度明文规定（R1-R6）

### R1：每个 verdict 必须附带 concrete evidence

| verdict | 所需证据 | ❌ 禁止写法 | ✅ 强制格式 |
|---------|---------|------------|------------|
| 组件存在 | 文件路径 + 关键代码行 | `QuestionDao 存在 ✅` | `data/daos/question_dao.dart:9-11 — const QuestionDao(this._db)` |
| 流程工作 | 每步箭头的输出→输入链 | `onAppStart 调了 checkAll ✅` | `sync_manager.dart:55 — 调了但返回值丢弃 ❌` |
| 测试通过 | 实际运行测试套件 | `全部通过 ✅` | `pytest -v — 21 passed ✅` |
| 设计符合 | 设计文档 + 代码逐字段对比 | `模型一致 ✅` | `数据库结构设计.md §3.1 vs models.py — 全部字段匹配 ✅` |

### R2：数据流追踪是强制性的

对设计文档描述的每个流程，逐箭头的输出→输入验证。

### R3："存在 ✅" 不是最终结论，是中间状态

每个"存在"必须继续判定为"工作正常"/"已断裂"/"不完整"。

### R4：各层最小探测深度

见各类审计的 layer-specific probes 表。

### R5：测试结果必须真实运行

不信任执行日志、commit message、计划文档的状态声明。

### R6：每个 async 方法必须检查返回值捕获

`await f()`（丢弃返回值）vs `var r = await f()`（捕获）。

## 五、四维放大镜（每个审计必须覆盖全部四个维度）

| # | 维度 | 核心问题 | 具体检查 |
|---|------|---------|---------|
| ① | **设计合规** | 代码与设计文档逐行对照？API 字段名和格式一致？ | 模型逐字段比对、API 响应 schema 比对、Serializer 接受但视图不保存的字段、UI 与 HTML 原型逐元素比对 |
| ② | **测试覆盖** | 每步必有测试？边界场景覆盖？ | 运行测试套件、检查测试文件是否存在、检查边界场景（空/不存在/无效/异常） |
| ③ | **边界异常** | 坏路径不崩？ | 断网/过期/非法输入/并发 4 类场景至少各有一个 |
| ④ | **敷衍应付** | 识别简化/v1/stub/TODO/预留？识别流程断裂？ | 扫描 stub 模式 + 返回值链追踪（R2/R6） |

**敷衍应付识别清单：**

| 模式 | 含义 | 风险评估 |
|------|------|---------|
| `// v1 方案` | 作者知道不完整 | 后续可能永远不来 |
| `// 极简版本` | 故意简化 | 检查切掉了什么：异常路径？边界情况？ |
| `// 预留` | 标记未来实现 | 当前代码错误地工作 |
| `// 待接入` | 依赖外部变更 | 依赖可能永远不实现 |
| `return []` / `return 0` | stub 返回默认值 | 调用方以为"没有数据" |
| `throw UnimplementedError` | 生产路径没构建 | 用户触发即闪退 |
| 注释说算法 X，代码做 Y | 静默简化 | 用户看到错误输出但没有报错 |
| `await f()` 返回值丢弃 | 流程断裂 | 组件存在但断开的伪实现 |

**判断 5 问：**
1. 简化切掉了异常路径吗？
2. 简化切掉了边界情况吗？
3. "后续"有具体的计划和负责人吗？
4. stub 返回了看起来合理的默认数据吗？
5. 简化在最终输出中可见吗？

## 六、六维框架（完整报告用）

| 维度 | 一句话本质 | 最低门槛 |
|------|-----------|---------|
| ① 设计合规 | 代码和设计文档对得上吗？ | models.py 与数据库设计.md 逐字段核对 |
| ② 数据正确 | 迁移/构建/同步的数据一条不丢？ | Audit 文件可阅，随机抽 3 条手工核对 |
| ③ 测试覆盖 | CI 上有测试看着吗？边界测了没？ | 该层测试全通过，关键边界场景有测试用例 |
| ④ 异常处理 | 不是理想路径走得好不好，而是坏路径崩不崩？ | 断网/过期/非法/并发 4 类异常至少各有一个场景处理了 |
| ⑤ 用户体验 | 真实教师觉得好用吗？ | 不是你觉得，是教师签字说了算 |
| ⑥ 安全部署 | 上线后不会半夜被叫醒吧？ | --deploy 检查通过、Sentry 有日志、备份就位 |

## 七、常见陷阱

| # | 陷阱 | 说明 |
|---|------|------|
| 1 | 执行日志已过时 | Fix 提交更新了代码但没更新执行日志。永远以实际文件和测试结果为准 |
| 2 | 计划状态已过时 | 计划文档的"已完成"/"未开始"标签可能无效。探测真实系统状态 |
| 3 | "我觉得不是阻塞"无效 | 只有验收检查清单决定阻塞等级。发现的问题全部呈现，由 Owner 判断 |
| 4 | "代码看起来很完整"最危险 | 绕过方法论。即使结果看起来明显也要走流程 |
| 5 | 冷却时序违规 | 冷却写入必须在所有操作成功后执行（R6） |
| 6 | 硬编码代替 SystemConfig | 设计文档要求从 assets.db 读取的参数，不在代码中写死 |
| 7 | 回调函数注册了但从未触发 | 函数作为参数传进去了，但没有任何代码调用它 |
| 8 | 忽略 HTML 原型 | 只读文字设计文档（页面设计说明.md）不读 HTML 原型 → 漏审 UI 差异 |
