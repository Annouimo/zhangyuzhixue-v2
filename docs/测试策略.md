## 二、第 1 层：纯算法单元测试

### 2.1 测试对象

Repository 文件尾部的私有类，纯逻辑，不依赖数据库/Widget/网络。

| 文件 | 私有类 | 测试内容 |
|------|--------|---------|
| `recommend_repository.dart` | `_RecommendationEngine` | 掌握度计算、时间衰减(7天半衰期)、小样本收缩(minConfidence=5)、路线A/B选材、合并排序、冷启动(5题阈值)、排除规则(已做对+3天内刚做错) |
| `achievement_repository.dart` | `_AchievementEngine` | 5类成就(LOGIN/PRACTICE/COURSE/PAPER/RATING)触发逻辑、阈值判断、防止重复解锁 |
| `rating_repository.dart` | `_PointsCalculator` | 三种积分(累计/学习/消耗/可用)实时计算公式、PAPER_PURCHASE 排除逻辑 |
| `statistics_repository.dart` | `_StatisticsAggregator` | 自适应粒度切换(bar/cal/week/month边界)、热力图染色归一化、折线图 SVG 数据点、环形图 conic-gradient 百分比 |
| `exam_repository.dart` | `_ExamFilterEngine` | 筛选条件组合过滤、题型 stepper 默认值、难度调优上下限动态计算 |
| `progress_repository.dart` | `_ProgressEngine` | 解题状态重建(首次/复访-已完成/复访-部分完成)、多解法多存档推算 |
| `lib/data/helpers/question_status_helper.dart` | — | 已做/进行中/未做三种状态推算 |
| `lib/data/helpers/lecture_parser.dart` | `parseMdContent()` | pagebreak/reveal 分隔符解析、pages[].blocks[] 输出结构、复习模式忽略分隔符 |

### 2.2 测试方法

```
输入:   纯 Dart 对象（List/Map/Set），不涉及数据库
执行:   调用私有类的 public 方法（算法入口）
断言:   输出结果是否符合预期
```

### 2.3 示例：_RecommendationEngine

```
测试用例清单（设计阶段，非代码）：

[冷启动]
  - answer_records.count = 0 → getSmartList() 返回 []
  - answer_records.count = 4 → 返回 []（< 冷启动阈值 5）
  - answer_records.count = 5 → 正常推荐（边界值）

[时间衰减]
  - 今天做的题权重 = 1.0
  - 7 天前做的题权重 = 0.5
  - 14 天前做的题权重 = 0.25
  - 30 天前做的题权重 ≈ 0.05

[小样本收缩]
  - 做题量 = 0 → 掌握度 = 0.5（纯收缩）
  - 做题量 = 3 → 掌握度向 0.5 部分收缩
  - 做题量 = 5 → 无收缩（达到 minConfidence）

[路线A - 概念掌握度]
  - 单概念多道题，正确率 100% → 掌握度 = 1.0
  - 单概念全错 → 掌握度 = 0.0
  - 概念无做题记录 → 跳过该概念

[路线B - 卡片卡住率]
  - 卡住权重: correct=0 / partial=0.5 / wrong=1
  - 卡住率 = 权重和 / 出现总步数
  - 出现 < 5 次向 0.5 收缩（同路线A）

[合并排序]
  - choice 最薄弱道在前，fill 次之，solution 最后
  - 不足时不补其他题型
  - maxChoice=2, maxFill=2, maxSolution=2
```

## 三、第 2 层：DAO + 数据库集成测试

### 3.1 测试对象

`lib/data/daos/` 目录下的所有 DAO 类，用 `NativeDatabase.memory()` 创建内存数据库。

### 3.2 测试范围

| DAO | 测试内容 | 数据库 |
|-----|---------|--------|
| `question_dao.dart` | 按 ID 查、按筛选条件搜索、按题型过滤 | assets.db |
| `assignment_dao.dart` | 按 course_id 查作业列表 | assets.db |
| `lecture_dao.dart` | 按 chapter_id 查讲义内容 | lectures.db |
| `progress_dao.dart` | submission_detail CRUD、step_feedback 跨表查询、按 attempt_number 筛选 | user.db |
| `rating_dao.dart` | question_rating 插入/覆盖/查询 | user.db |
| `sync_queue_dao.dart` | enqueue → pending → inProgress → done/failed 状态迁移 | user.db |
| `achievement_dao.dart` | student_achievement 进度查询/更新 | user.db |
| `statistics_dao.dart` | 跨表统计查询（做题量/正确率/积分趋势/题型分布） | user.db |
| `exam_dao.dart` | custom_paper + paper_question 事务写入 | user.db |
| `user_dao.dart` | user_profile CRUD、points_transaction 查询 | user.db |

### 3.3 测试方法

```
前置:   在 memory DB 中插入测试数据（通过 drift 的 API）
执行:   调用 DAO 方法
断言:   查询结果与预期一致
清理:   测试用例结束后 memory DB 自动销毁
```

### 3.4 测试数据策略

- assets.db 的测试数据：构造精简的小型数据集（如 5 道题、2 个解法、3 个步骤），覆盖所有表结构
- lectures.db 的测试数据：2 个课程、每课程 2 章、每章 1 讲讲义（含分隔符）
- user.db 的测试数据：每个测试用例独立构造，互不干扰

### 3.5 核心边界测试

```
[sync_queue 状态机]
  - enqueue → status = pending
  - pushAll() 开始处理 → status = inProgress
  - 请求成功 → status = done → cleanup 删除
  - 请求失败(网络) → status = failed, retryCount++
  - retryCount >= maxRetries(5) → permanentFailure
  - 7 天后 cleanup 删除 permanentFailure
  - App 被杀后 inProgress 记录下次启动重新取出

[三库打开/替换]
  - DatabaseProvider.init() 正确打开三个数据库
  - replaceAssetsDb() 关闭旧连接 → 覆盖文件 → 重新打开
  - clearUserDb() 清空 user.db 数据
```

## 六、第 5 层：E2E 全流程测试

### 6.1 什么是 E2E 测试（解释）

E2E（端到端）测试模拟真实用户操作，从 App 启动到功能完成的完整路径。与前几层的区别：

| 测试类型 | 测什么 | 真实设备/网络 | 数据源 |
|---------|-------|-------------|--------|
| 单元测试 | 一个函数 | ❌ 不需要 | 纯内存 |
| DAO 测试 | 数据访问 | ❌ 不需要 | memory DB |
| Repository 测试 | 数据组装 | ❌ 不需要 | memory DB |
| Widget 测试 | 组件渲染 | ❌ 不需要 | mock 数据 |
| E2E 测试 | 完整用户流程 | ✅ 需要 | 真实服务器或本地 server |

在章鱼智学这个项目中，E2E 测试验证的是「数据在真实 SQLite 数据库、真实 Drift DAO、真实 Repository、真实 UI 之间完整流转」——它不是验证 UI 样式，而是验证**功能正确性和数据一致性**。

### 6.2 关键流程

#### 流程 A：用户注册 → 登录 → 首页显示

```
App 启动
  ↓
检查 SharedPreferences（无 token）
  ↓
显示登录页
  ↓
输入用户名/密码 → 点击登录
  ↓
POST /api/v1/auth/login/ → 返回 token
  ↓
Token 写入 SharedPreferences
  ↓
跳转到首页
  ↓
验证：首页 4 个 Tab 正确显示
验证：用户昵称/头像已加载
验证：待办作业计数显示
验证：退出 App 重新打开 → 自动恢复登录（不显示登录页）
```

**为什么需要 E2E：** 涉及 Flutter Widget、SharedPreferences、Dio 拦截器、JWT 刷新、路由跳转 5 个模块的协作，任一环节出错都不可用。无法被低层测试覆盖。

#### 流程 B：做一道选择题（离线可做）

```
进入"作业"Tab
  ↓
选择作业 → 进入作业详情 → 点击题目
  ↓
入口页判断：无 submission_detail 记录 → mode=first
  ↓
路由到 solve-choice.html?mode=first
  ↓
显示题目（题干 + 选项）
  ↓
5 秒冷却 → 按钮恢复
  ↓
用户选择选项 A → 点击提交
  ↓
结果显示（绿色=A 正确 / 红色=A 错误+绿色标正确答案）
  ↓
🎉 已完成横幅 → [下一题] [⭐ 评分]
  ↓
验证：submission_detail 表写入一条记录
验证：is_correct 值正确
验证：sync_queue 表追加一条 pending 记录
验证：退出重进同一题 → 直接展示历史结果（不复访冷却）
```

**为什么需要 E2E：** 涉及冷却计时器、选项交互、提交逻辑、结果颜色语义（蓝色选中/绿色正确/红色错误）、DB 写入、同步队列入队、复访重建——横跨 UI + Repository + DAO + sync。

#### 流程 C：做一道解答题（多步 + 知识卡片）

```
进入解答题 → solve-map?mode=first（欢迎卡片）
  ↓
点击"开始" → solve-step?mode=first
  ↓
第 1 步：5 秒冷却 → 点击箭头 ▶ → 解析展开 → feedback 按钮出现
  ↓
用户点击"全对" → 进入第 2 步
  ↓
第 2 步：同上 → 用户点击"不会" → 知识卡片弹层弹出
  ↓
卡片弹层中反馈"了解" → 关闭弹层
  ↓
（重复至最后一步）
  ↓
全部完成 → 🎉 已完成横幅
  ↓
验证：step_feedback 表每条步骤一条记录
验证：card_feedback 表写入 mastery_status
验证：submission_detail.status = completed
验证：sync_queue 包含 submission + N×step_feedback + M×card_feedback
```

**为什么需要 E2E：** 解答题 v2 架构（存档/多周目/支线）是整个项目最复杂的交互；冷却→展开→反馈的序列状态机无法被 Widget 测试完整覆盖；多表事务写入(step_feedback + card_feedback + submission_detail)的一致性必须真实跑通。

#### 流程 D：离线做题 → 上线自动同步

```
1. 断开网络
2. 做 3 道题（选填 + 解答）
3. 验证：本地能看到全部完成状态
4. 恢复网络
5. 触发同步（手动点击"全部重试"或重启 App）
6. 验证：POST /api/v1/sync/push/ 成功
7. 验证：服务端 DB 中能看到这 3 道题的提交记录
8. 验证：sync_queue 中对应条目标记为 done
```

**为什么需要 E2E：** 同步引擎是本地优先架构的关键环节——队列状态机、LWW 冲突处理、server_id 回填、批量推送粒度的正确性，只有 E2E 测试能完整验证。

#### 流程 E：数据库更新

```
1. 启动 App（当前的 assets.db）
2. API 返回 data_version 更高
3. 弹窗提示更新
4. 用户点击"立即更新"
5. 下载 .db.gz → 校验 checksum → 替换 .db
6. 界面恢复到首页
7. 验证：新版本的题目可正常浏览
```

**为什么需要 E2E：** 更新机制涉及下载、文件替换、Drift 连接重开、UI 恢复——这些在单元/集成测试中无法模拟。

## 七、第 6 层：服务端 API 契约测试

### 7.1 设计阶段：接口契约定义

每支 API 的测试契约 = 请求格式 + 预期响应格式 + 错误码 + 权限要求。

测试代码待 `server/` 目录创建后补写，但契约在设计阶段先定下来。

### 7.2 契约列表

#### 认证 API

```
[POST /api/v1/auth/login/]
  请求: {username, password, app_type}
  成功: {code:0, data:{access, refresh, user:{id, username, role, ...}}}
  错误: code=40001（用户名或密码错误）
  错误: code=40003（app_type 与角色不匹配）
  验证: access token 24h 内有效
  验证: 返回的 role 与 Student/Teacher 表一致

[POST /api/v1/auth/register/]
  请求: {invitation_code, username, password, real_name, phone?, gaokao_year?}
  成功: {code:0, message:"注册成功，请登录"}
  错误: code=40101（邀请码无效/已使用/已过期）
  错误: code=40102（用户名已存在）
  验证: 不返回 token
  验证: User + Student 记录创建成功

[POST /api/v1/auth/refresh/]
  请求: {refresh}
  成功: {code:0, data:{access, refresh}}
  错误: code=40002（refresh token 过期）
```

#### 同步 API

```
[GET /api/v1/sync/qbank/version/]
  认证: 不需要 token（登录前即可检查）
  成功: {code:0, data:{schema_version, data_version, force_update, message, download_url, checksum, size_bytes}}
  验证: 无 token 也可返回

[GET /api/v1/sync/lecture/version/]
  （同 qbank/version，仅 data 含义不同）

[POST /api/v1/sync/push/]
  请求: {batch: [{entity_type, operation_type, payload}]}
  成功: {code:0, data:{server_ids: {entity_type: {local_id: server_id}}}}
  错误: code=40301（payload 校验失败）
  错误: code=40302（LWW 冲突）
  验证: 忽略请求体中的 student_id（从 token 解析）
  验证: batch 顺序处理
  验证: 同一 batch 在同一事务中
```

### 7.3 测试方法

```
框架:   pytest + django-rest-framework 的 APIClient

每个端点的测试用例：
  - 请求格式正确 → 断言响应 code=0
```

## 九、测试数据策略

### 9.1 数据来源

| 测试层 | 数据来源 |
|--------|---------|
| 算法单元 | 纯内存构造（List/Map） |
| DAO 集成 | memory DB 中逐条插入 |
| Repository 集成 | memory DB 中逐条插入 |
| Widget | 硬编码测试数据或 Repository Mock |
| E2E | 真实 assets.db + 测试服务器 |
| 服务端契约 | Django fixtures + 独立测试 DB |
| 构建/更新 | 真实构建产物（.db.gz） |

### 9.2 测试数据要求

- 每个测试用例独立构造数据，不共享状态
- 测试用例结束后清理（memory DB 自动销毁 / 测试 DB 重置）
- 测试数据覆盖边界情况：空表、单条、大量数据（性能测试用）
- 不要在测试之间共享 `DatabaseProvider` 单例（否则测试顺序影响结果）

### 9.3 Flutter 测试 concurrency

- 单元测试和 DAO 测试可以并行运行
- Widget 测试和 Repository 测试建议串行（涉及 Flutter 引擎）
- E2E 测试互相独立，可串行执行

## 十一、优先级与实施顺序

| 优先级 | 层 | 理由 |
|--------|----|------|
| **P0** | 第 6 层（服务端契约） | 服务端 P0 实现完后立即写，保证 API 正确性 |
| **P0** | 第 1 层（算法单元） | 5 个复杂算法类，最容易测也最值得先测 |
| **P1** | 第 2 层（DAO 集成） | 保证 DB 操作正确，支撑上层测试 |
| **P1** | 第 3 层（Repository 集成） | Repository 是 UI 层直接消费的数据源 |
| **P2** | 第 4 层（Widget） | 核心组件需要 UI 测试覆盖 |
| **P2** | 第 7 层（构建/更新） | 构建脚本上线前必须验证 |
| **P3** | 第 5 层（E2E） | 需要测试服务器环境，等基础功能稳定后补 |
