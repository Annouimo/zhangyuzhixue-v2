# 章鱼智学 v2 · 验收检查清单

> **用途：** 项目 Owner（你）在每 Phase 完成后，从六个维度检查是否达到"可进入下一阶段"的标准。
> **使用方法：** 每 Phase 完成后，逐一排查该 Phase 的检查项。全部打勾后签字放行下一 Phase。
> **第零原则：** 这不是替测试人员跑用例，而是 Owner 层面的"兜得住吗？"式查验。每个检查项都是5分钟内能确认的。

---

## 一、验收六维体系

每个 Phase 的检查项按以下 6 个维度组织：

| 维度 | 一句话本质 | 最低门槛 |
|------|-----------|---------|
| **① 设计合规** | 代码和设计文档对得上吗？有没有擅自加东西？ | models.py 与数据库设计.md 逐字段核对，没有"我也不知道为什么加了这个字段" |
| **② 数据正确** | 迁移/构建/同步的数据一条不丢、一条不多？ | Audit 文件可阅，随机抽 3 条手工核对 |
| **③ 测试覆盖** | CI 上有测试看着吗？边界测了没？ | 该层测试全通过，关键边界场景有测试用例 |
| **④ 异常处理** | 不是理想路径走得好不好，而是坏路径崩不崩？ | 断网/过期/非法/并发 4 类异常至少各有一个场景处理了 |
| **⑤ 用户体验** | 真实教师觉得好用吗？ | 不是你觉得，是教师签字说了算 |
| **⑥ 安全部署** | 上线后不会半夜被叫醒吧？ | --deploy 检查通过、Sentry 有日志、背份就位 |

## 三、验收工作流

```
[开发者提交完成声明]
    ↓
[Owner 打开本清单该 Phase 页面]
    ↓
┌── 逐项检查 ──────────────────┐
│ ① 看代码/文件（设计合规性）     │
│ ② 看 audit 产物（数据正确性）   │
│ ③ 看 CI + 本地测试（测试覆盖）   │
│ ④ 问一个坏路径问题（异常处理）   │
│ ⑤ 教师签字/亲自感受（用户体验）  │
│ ⑥ 看安全配置（安全部署）        │
└──────────────────────────────┘
    ↓
┌── 判断 ──────────────────────┐
│ 全部通过 → 签字放行             │
│ 有非阻塞问题 → 记录"Phase N+1 前修复"签字放行 │
│ 有阻塞问题 → 驳回，说明原因      │
└──────────────────────────────┘
```

### 验收门槛诠释

| 结论 | 含义 |
|------|------|
| ✅ 通过 | 该 Phase 达到了"可进入下一阶段"的质量标准。不是 100% 完美，但没有阻塞性问题 |
| ⚠️ 有条件放行 | 少量非阻塞问题记录到下一 Phase 的"须修复"列表，当前阶段可继续 |
| ❌ 驳回 | 有阻塞问题（数据丢失、API 契约不匹配、安全漏洞、核心路径不通），需修复后再审 |

## 四、全局截止条件

以下问题如果在 Phase N 发现了但没修，必须在下一个 Phase 开始前修复，不能攒到最后：

| 问题类型 | 举例 | 最晚修复 Phase |
|---------|------|---------------|
| 数据迁移错误 | 题数不对、字段映射错 | Phase 2 前 |
| API 契约不匹配 | Flutter 端和服务端端点的参数/返回值不一致 | Phase 2.4 前 |
| 安全漏洞 | JWT 配置错误、PDF 签名可伪造 | **立即修复，不进入下一 Phase** |
| CI 红 | 流水线不通过 | **不进入下一 Phase** |
| 核心路径不通 | 登录后白屏、做题提交无响应 | Phase 3.5 教师 UAT 前 |
