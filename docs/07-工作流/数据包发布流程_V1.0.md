# 数据包发布流程 V1.0

## 适用范围

本流程只发布客户端公共数据库包：

- `qbank_vN.db.gz`：题库数据；
- `courses_vN.db.gz`：课程数据。

历史 `lecture`、图片包、Flutter 安装包不在本流程范围内。生产服务器固定为
`82.157.115.219`，正式包目录为
`/opt/zhangyuzhixue-v2/server/media/db/`。

## 发布门禁

发布入口为 `scripts/deploy_data_bundle.ps1`。默认仅执行 dry-run，并检查：

1. gzip 可完整解压；
2. SQLite `integrity_check` 和 `foreign_key_check`；
3. `meta` 表中的 schema/data 版本；
4. 文件名必须是 `<type>_v<data_version>.db.gz`；
5. 清单中的大小、SHA-256 和数据库版本一致；
6. 正式发布时，data version 必须严格高于生产当前版本；
7. 本地包存在未提交修改时拒绝发布，除非明确传入 `-AllowDirty`。

题库 dry-run 示例：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\deploy_data_bundle.ps1 `
  -DbType qbank -Bundle path\to\qbank_v27.db.gz
```

审查生成的 manifest 后，正式发布增加 `-Deploy`。`-ForceUpdate` 和
`-Message` 只在产品负责人确认客户端升级策略后使用。

## 服务器端事务边界

服务器端发布器 `server/scripts/release_db_bundle.py` 使用单实例文件锁。发布时：

1. 在写入生产前再次验证上传包和 manifest；
2. 将原目标文件和原 `DbVersion` 元数据保存到
   `/var/backups/zhangyuzhixue-v2/data-bundles/<release-id>/`；
3. 在 `media/db` 同一文件系统内暂存，并用 `os.replace` 原子切换文件；
4. 在 Django `transaction.atomic()` 中锁定并更新对应 `DbVersion`；
5. 写入 `/var/backups/zhangyuzhixue-v2/data-bundles/releases.log`。

本地入口随后从公网版本 API 读取本次版本，下载正式包并再次验证大小、哈希、
gzip、SQLite 完整性和版本。公网验证失败时，入口自动调用服务器端 rollback，
只恢复该数据类型的元数据和本次目标文件，不覆盖整个业务数据库。

## 手工回滚

自动回滚失败时，先停止新的数据包发布，再使用发布日志中的 release ID：

```bash
sudo -u ubuntu /opt/zhangyuzhixue-v2/venv/bin/python \
  /opt/zhangyuzhixue-v2/server/scripts/release_db_bundle.py rollback \
  --project-root /opt/zhangyuzhixue-v2/server \
  --backup-root /var/backups/zhangyuzhixue-v2/data-bundles \
  --lock-file /opt/zhangyuzhixue-v2/server/media/db/.release.lock \
  --release-id <release-id>
```

回滚后必须重新调用相应版本 API，并下载包校验。不要通过 SQLite 命令手工修改
生产 `DbVersion`。

## 尚未纳入

Windows、Android、iOS 客户端安装包仍需要独立的制品存储、渠道签名和版本发布
流程。`create_release_manifest.py` 当前只负责本地 Windows 制品清单，不能替代生产
客户端发布。
