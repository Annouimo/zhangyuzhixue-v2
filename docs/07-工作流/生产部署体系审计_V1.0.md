## 1. 结论

当前部署边界总体合理：Django 服务端通过 bare Git 仓库和 `post-receive` hook 发布，Landing 由 nginx 独立直出，教师 Web、nginx、Cloudflare Tunnel、数据库备份和客户端制品各有不同生命周期。

问题不在于“服务端和 Landing 分开发布”，而在于这些边界原先没有形成统一、可重复、可审计的发布体系。本轮已经补充服务端并发锁、预发布门禁、数据库 shadow migration、离线 wheelhouse、版本化 venv、健康检查、发布记录和 Landing 发布脚本。主要流程已标准化，后续工作转为监控与定期演练维护。

## 5. 审计发现

### P0：生产敏感文件权限过宽

| 文件 | 当前权限 | 要求 |
|---|---:|---:|
| `server/.env` | `664 ubuntu:ubuntu` | `600 ubuntu:ubuntu` |
| `zhangyuzhixue.zhtec123.com/privkey.pem` 目标文件 | `644 root:root` | `600 root:root` |
| Cloudflare Tunnel credentials JSON | `644 root:root` | `600 root:root` |

`zhangyuzhixue.top` 的 Let's Encrypt 私钥目标文件已经是正确的 `600`。上述权限修复不改变文件内容，但应在单独维护窗口执行，并在修复后验证 nginx、cloudflared 和 Gunicorn 仍可读取。

### P1：服务端 hook 缺少发布互斥锁

连续或并发 push 可能同时执行数据库备份、checkout、migration、依赖安装和服务重启。应使用 `flock` 锁定单一生产发布。

### P1：migration 直接作用于生产数据库

hook 在生产数据库上直接执行 `migrate`。虽然失败时恢复数据库备份，但没有先在固定 shadow 目录验证 migration、`integrity_check` 和 `foreign_key_check`。应把 shadow migration 作为生产 mutation 前的阻断门禁。

### P1：服务端 checkout 不清理已删除文件

当前命令只 checkout `server/` 路径。新版本已删除的文件可能继续残留在生产目录。目标实现应先生成完整 release 目录，再原子切换，或明确清理受 Git 管理但新 revision 已删除的文件，同时保护 `.env`、数据库、media 和运行时文件。

### P1：Landing 没有正式发布脚本

本次已验证“本地检查 -> manifest -> 上传临时目录 -> 服务器备份 -> checksum -> 精确覆盖 -> 权限修复 -> nginx 检查 -> 公网回归”的流程，但仓库内没有可重复入口，也没有 release manifest 和部署日志。

### P1：生产依赖在发布时在线安装

原 hook 在共享 venv 上直接执行在线 `pip install -r requirements.txt`。现已改为先下载目标 revision 的完整 wheelhouse，再在 `/opt/zhangyuzhixue-v2/venvs/<commit>` 构建独立环境，正式安装强制使用 `--no-index`。migration 与 collectstatic 通过新环境验证后才原子切换 `/opt/zhangyuzhixue-v2/venv`；健康检查失败会切回旧环境。

### P2：健康检查覆盖不足

当前 hook 仅检查 systemd、Admin 和登录接口 GET=405。发布后还应验证：

- 本机 `127.0.0.1:8001`；
- 两个 HTTPS 域名；
- API、Admin、PDF、static、media 路由；
- Landing、教师 Web、robots、sitemap 和品牌 404；
- migration 状态、数据库完整性与外键完整性。

### P2：发布记录与版本关联不足

服务器上没有统一记录一次 release 的 commit、manifest、部署时间、部署人、数据库备份、验证结果和回滚目标。需要 append-only 部署日志，且不得记录 secret。

### P2：本地部署脚本和 hook 职责重叠

`deploy_prod.sh` 负责 preflight、push 和发布后检查，hook 负责真正 mutation，但两边检查项不一致。应把通用检查拆为可独立运行的生产 smoke 脚本，避免两套口径漂移。

### P3：文档存在历史方案干扰

仓库仍包含已放弃的 `43.137.3.138` Docker 草案以及旧服务器相关历史记录。历史文档可以保留，但必须明确标记“未执行/已废弃”，避免再次被当作生产事实。

## 6. 目标发布流程

### 6.1 服务端

1. 要求工作区干净、目标 commit 已提交且 CI 通过。
2. 只允许从 `master` 非 force push 到生产 remote。
3. 服务器取得全局发布锁。
4. 检查磁盘、服务、`.env`、备份目录和依赖缓存。
5. 使用 Online Backup API 生成 pre-deploy 数据库快照并校验。
6. 在固定 `/tmp/zhangyuzhixue-shadow/` 中恢复数据库副本。
7. 对 shadow DB 执行目标 revision 的 migration、Django checks、完整性和外键检查。
8. 构建独立 release 目录并准备依赖、static。
9. 停止或平滑切换 Gunicorn，应用 production migration。
10. 原子切换当前 release，启动服务。
11. 执行统一 smoke tests。
12. 记录 release manifest；失败则恢复代码、数据库和服务。

### 6.2 Landing

1. 只允许发布明确清单，不整体覆盖 `landing/`。
2. 本地验证 HTML、内部链接、图片、SEO、robots、sitemap、404 和响应式页面。
3. 生成 SHA-256 manifest 和 release archive。
4. 上传到服务器临时目录并复核 manifest。
5. 备份当前 Landing。
6. 解包到 staging 目录，设置目录 `755`、文件 `644`。
7. 精确覆盖公共站；教师 Web 是否包含在 release 中必须显式选择。
8. 如包含 nginx 变更，先备份配置，`nginx -t` 通过后 reload，失败自动恢复。
9. 从公网验证页面、资源、下载链接、教师端和品牌 404。
10. 记录 manifest、备份位置和回滚命令。

### 6.3 nginx / Tunnel

- nginx 配置纳入仓库模板，但证书路径和生产参数通过受控变量维护。
- 配置变更必须经过 `nginx -t` 和自动回滚，不与普通服务端代码发布隐式绑定。
- Cloudflare Tunnel 配置变更必须先验证凭据权限、ingress hostname 和本地 upstream，再单独 restart。

## 7. 实施顺序

1. **P0 权限修复**：`.env`、API 域名私钥、Tunnel credentials。
2. **Landing 发布脚本**：先固化已经成功验证的低耦合流程。

## 13. 固定 commit 发布入口

- `deploy_prod.sh` 在任何网络操作前记录 `RELEASE_COMMIT=$(git rev-parse HEAD)`。
- 推送使用 `<固定哈希>:refs/heads/master`，不再使用会随并发任务移动的裸 `master`。
