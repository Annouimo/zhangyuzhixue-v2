# 章鱼智学 · 数据访问层设计草案

> 数据访问层位于 Repository/Domain 层之下、本地持久化层之上，
> 是 Repository 与 SQLite/Sync/API 之间的桥梁。
> 本文档定义该层的文件结构、接口约定及关键交互流程。

---

## 一、层间契约

Repository 层通过**两种接口**访问数据，不直接接触 Dio 或 Drift 连接：

```
┌─────────────────────────────────────────┐
│  Repository（13 个，静态方法）             │
│  调用 daos.*DAO 读 DB + 调用 api.*Api 写  │
└────────────┬──────────────────┬─────────┘
             │ 读               │ 写
             ▼                  ▼
┌────────────────────┐ ┌──────────────────────┐
│ DAO 层             │ │ API Client +         │
│ (Drift 表 CRUD)    │ │ Sync Engine (推送)   │
└────────────────────┘ └──────────────────────┘
```

**约定：**
- Repository **只引用 DAO 和 Api**，不直接持有 Drift Database 或 Dio
- DAO 和 API 均为**全局单例 + 静态访问**（与 Repository 的静态方法风格一致）
- Repository 不接触 SharedPreferences，纯客户端状态由各页面的 `_Prefs` 直接操作

## 三、Database 层设计

### 3.1 三库方案

| 数据库 | 类 | 连接 | 读写 | 生命周期 |
|-------|------|------|------|---------|
| assets.db | `AssetsDatabase` | Drift | 只读 | 打开 → 替换时关闭重开 |
| lectures.db | `LecturesDatabase` | Drift | 只读 | 同上 |
| user.db | `AppDatabase` | Drift | 读写 | 打开 → 登出时清空 → 重开 |

### 3.2 DatabaseProvider（生命周期管理）

```dart
/// 三库生命周期管理，全局单例
class DatabaseProvider {
  static final DatabaseProvider _instance = DatabaseProvider._();
  factory DatabaseProvider() => _instance;

  AppDatabase? _appDb;       // user.db（读写）
  AssetsDatabase? _assetsDb;  // assets.db（只读）
  LecturesDatabase? _lecturesDb; // lectures.db（只读）

  /// 初始化：打开三个数据库连接
  Future<void> init() async {
    final dir = await getApplicationDocumentsDirectory();
    _assetsDb = AssetsDatabase(await _openDb('${dir.path}/assets.db'));
    _lecturesDb = LecturesDatabase(await _openDb('${dir.path}/lectures.db'));
    _appDb = AppDatabase(await _openDb('${dir.path}/user.db'));
    // 执行迁移
    await _appDb!.migrate();
  }

  // ── 对外暴露 ──
  AppDatabase get appDb => _appDb!;
  AssetsDatabase get assetsDb => _assetsDb!;
  LecturesDatabase get lecturesDb => _lecturesDb!;

  // ── 更新替换 ──
  /// 替换 assets.db（关闭旧连接 → 覆盖文件 → 打开新连接）
  Future<void> replaceAssetsDb(String newPath) async { … }
  /// 替换 lectures.db
  Future<void> replaceLecturesDb(String newPath) async { … }
  /// 清空 user.db（登出时）
  Future<void> clearUserDb() async { … }
}
```

### 3.3 DAO 访问方式

每个 DAO 采用 **静态工厂获取实例**，从 DatabaseProvider 中取对应数据库：

```dart

  QuestionDao._(this._db);

  static QuestionDao _instance = QuestionDao._(DatabaseProvider().assetsDb);
  factory QuestionDao() => _instance;

  // ── 查询（返回 Drift 生成的 DataClass） ──
  Future<Question?> getById(int id) =>
      _db.questionDao.getById(id); // 委托 drift 的 generated DAO

  Future<List<Question>> search(QuestionFilter filter) async { … }
}

class SyncQueueDao {
  SyncQueueDao._(this._db);
  final AppDatabase _db;

  static SyncQueueDao _instance = SyncQueueDao._(DatabaseProvider().appDb);
  factory SyncQueueDao() => _instance;

  Future<List<SyncQueueEntry>> getPending() => _db.syncQueueDao.getPending();
  Future<void> markDone(int localId) => _db.syncQueueDao.markDone(localId);
  Future<void> markFailed(int localId, String error) => …;
}
```

### 3.4 测试性设计

静态工厂不代表不可测试。两个缓解措施：

**（a）DAO 可替换** — 每个 DAO 暴露 `@visibleForTesting setInstance()`，测试时注入 mock DAO 或基于 Drift in-memory database 的 real DAO。

```dart
class QuestionDao {
  QuestionDao._(this._db);
  final AssetsDatabase _db;

  static QuestionDao _instance = QuestionDao._(DatabaseProvider().assetsDb);
  factory QuestionDao() => _instance;

  @visibleForTesting
  static void setInstance(QuestionDao mock) => _instance = mock;
}

// ── 测试示例 ──
void main() {
  test('Repository 使用 in-memory DB', () async {
    final db = AssetsDatabase(NativeDatabase.memory());
    QuestionDao.setInstance(QuestionDao._(db));
    // … 测试 Repository 方法
  });
}
```

**（b）API Client 通过 Dio MockAdapter 测试**，不依赖 mock 替换：

```dart
void main() {
  test('API 请求', () async {
    final dio = ApiClient().dio;
    dio.mockAdapter = MockAdapter();
    // … 测试 API 调用
  });
}
```

这种模式**不需要 DI 框架**，后期引入 GetIt/Riverpod 时只需将 `setInstance` 改为 `Provider` 赋值，零架构变更。

## 四、API Client 层设计

### 4.1 单例 + 拦截器链

```dart
class ApiClient {
  static final ApiClient _instance = ApiClient._();
  factory ApiClient() => _instance;

  late final Dio _dio;

  void init({String baseUrl = 'https://zhangyuzhixue.top/api/v1/'}) {
    _dio = Dio(BaseOptions(
      baseUrl: baseUrl,
      connectTimeout: const Duration(seconds: 10),
      receiveTimeout: const Duration(seconds: 15),
      headers: {'Content-Type': 'application/json'},
    ));

    _dio.interceptors.addAll([
      _AuthInterceptor(),      // 附加 Bearer token
      _RefreshInterceptor(),   // 401 → 刷新 token → 重试
      _ErrorInterceptor(),     // 统一解析 {code, message, data}
    ]);
  }

  Dio get dio => _dio;
}
```

### 4.2 三个拦截器的职责

| 拦截器 | 顺序 | 职责 |
|-------|------|------|
| `_AuthInterceptor` | 请求前 | 从 `AppPrefs().getToken()` 读取 accessToken，附加 `Authorization: Bearer ***` |
| `_RefreshInterceptor` | 请求后(401) | 收到 401 → 检查是 access 过期还是 refresh 也过期 → 前者则调 `/auth/refresh/` 更新 token → 重试原请求；后者则清除 token 跳登录页 |
| `_ErrorInterceptor` | 请求后(所有) | 统一解析 `{code, message, data}` 格式，code≠0 时转为 `ApiException(code, message)` |

**Token 刷新关键时序（同步等待）：**

```
请求 A → 401
       → 获取 RefreshInterceptor 锁（mutex）
       → 调 POST /auth/refresh/
       → 成功 → 更新内存+SP中的 accessToken
       → 释放锁 → 重试请求 A
并行请求 B → 401
          → 等锁释放（不重复调 refresh）
          → 用新 accessToken 重试请求 B
```

> 锁机制保证并发 401 时不重复刷新 token，只有一个请求发起 refresh，其余等待。

### 4.3 ApiException

```dart
class ApiException implements Exception {
  final int code;      // 服务端返回的 code（40001 等）
  final String message; // 人类可读错误描述
  final int? httpStatus; // HTTP 状态码

  bool get isAuthError => code >= 40001 && code <= 40099;
  bool get shouldRetry => code >= 50001; // 服务端错误可重试
}
```

```dart
class SyncApi {
```

## 五、Network 层设计

```dart
/// 网络状态监听器
class ConnectivityMonitor {
  static final ConnectivityMonitor _instance = ConnectivityMonitor._();
  factory ConnectivityMonitor() => _instance;

  final _connectivity = Connectivity();
  final _stateController = BehaviorSubject<bool>.seeded(true);

  /// 当前是否在线
  bool get isOnline => _stateController.value;
  Stream<bool> get onConnectivityChanged => _stateController.stream;

  void init() {
    _connectivity.onConnectivityChanged.listen((result) {
      _stateController.add(result != ConnectivityResult.none);
    });
  }

  void dispose() => _stateController.close();
}
```

## 六、SharedPrefs 封装层

### 6.1 AppPrefs（仅封装全局 key）

```dart
/// SharedPreferences 封装，提供类型安全访问。
/// 仅封装**全局性**的 key，页面级的冷却/引导标记由各页 _Prefs 直接操作。
class AppPrefs {
  static final AppPrefs _instance = AppPrefs._();
  factory AppPrefs() => _instance;

  SharedPreferences? _prefs;

  Future<void> init() async {
    _prefs = await SharedPreferences.getInstance();
  }

  // ── Token ──
  String? get accessToken => _prefs!.getString(PrefixKeys.accessToken);
  Future<bool> saveAccessToken(String token) =>
      _prefs!.setString(PrefixKeys.accessToken, token);

  String? get refreshToken => _prefs!.getString(PrefixKeys.refreshToken);
  Future<bool> saveRefreshToken(String token) =>
      _prefs!.setString(PrefixKeys.refreshToken, token);

  // ── 用户缓存 ──
  Map<String, dynamic>? get userCache { … }
  Future<bool> saveUserCache(Map<String, dynamic> user) => …;

  // ── 版本号 ──
  int get qbankVersion => _prefs!.getInt(PrefixKeys.qbankVersion) ?? 0;
  int get lectureVersion => _prefs!.getInt(PrefixKeys.lectureVersion) ?? 0;

  // ── App 状态 ──
  Future<bool> clearAll() => _prefs!.clear();
}

/// SharedPreferences key 常量（全局）
class PrefixKeys {
  static const String accessToken = 'app_auth_token';
  static const String refreshToken = 'app_refresh_token';
  static const String userCache = 'app_user_cache';
  static const String qbankVersion = 'app_qbank_version';
  static const String lectureVersion = 'app_lecture_version';
  static const String updateLastShown = 'app_update_last_shown';
  // … 其他全局 key
}
```

### 6.2 AppPrefs 与 _Prefs 的分工边界

| 归属 | 封装方式 | 管理哪些 key | key 命名 |
|------|---------|-------------|---------|
| **AppPrefs**（本文件） | 类型安全方法 | `app_auth_token`, `app_refresh_token`, `app_user_cache`, `app_qbank_version`, `app_lecture_version`, `app_update_last_shown` | 全局性 key 以 `app_` 开头 |
| **_Prefs**（各页面内） | 直接操作 `SharedPreferences.getString/setString` | `solve_last_submit_{qid}`, `solve_rating_cooldown`, `{page}_guide_done` | 页面级 key 以**页面缩写**开头 |

**为什么不分批落入 AppPrefs？** 页面级 key 太多（每页可能有 2~5 个），且页面特有。全部集中到 AppPrefs 会造出几十个 getter/setter，维护成本高。页面自管的模式更轻量。

**防 key 冲突的规范：** AppPrefs 的 key 以 `app_` 开头，页面级 _Prefs 的 key 以**页面缩写**开头（如 `solve_`、`preference_`、`lecture_`），两套命名空间前缀完全不同，永远不会互相覆盖。已在 Flutter代码规范.md §1.5 中定义，此处重申。

```dart
class QuestionRepository {
```

## 八、需要决策的项目

| # | 问题 | 选项 | 我的建议 |
|---|------|------|---------|
| 1 | DAO 实例获取方式 | A) 静态工厂 `QuestionDao()` / B) 依赖注入 GetIt / C) Repository 构造注入 | **A** — 与当前 Repository 的 static 风格一致，零改动成本。测试通过 `@visibleForTesting setInstance()` 解决 |
| 2 | Drift 用 generated DAO 还是手写 SQL | A) 复用 Drift 生成的 `_$XxxDao` / B) 全手写 | **A** — Drift 的 DAO 生成已支持基础 CRUD，复杂 JOIN 在 Repository 层拼装 |
| 3 | Token 刷新用同步锁还是异步队列 | A) `Lock(mutex)` 同步等待 / B) 异步队列排队 | **A** — 实现简单，并发 401 场景极少 |
| 4 | AppPrefs 是否覆盖全部 SP key | A) 全部集中 / B) 只封装全局 key，页面级 key 留在 _Prefs | **B** — 页面 key 太多且页面特有，集中到 AppPrefs 会膨胀。防冲突靠命名前缀约定（`app_` vs `solve_`/`preference_`/`lecture_`） |
| 5 | ConnectivityMonitor 在哪儿初始化 | A) App 启动时 / B) 懒加载 | **A** — 需要尽早监听状态 |
| 6 | 三库是否用同一个 Drift 连接管理 | A) 各自独立 Database 类 / B) 合成一个 | **A** — 生命周期不同（assets/lectures 整库替换，user 不清），拆开更干净 |

## 九、与 Sync Engine 的边界

同步引擎（`spec/sync/sync_manager.dart`）当前写的是：
```dart
// await SyncManager().init(db, dio);
```

定稿后调整为：
```dart
await SyncManager().init(
  syncQueueDao: SyncQueueDao(),  // DAO 读 user.db 的 sync_queue 表
  apiClient: ApiClient().dio,     // 复用 API Client 的 Dio 实例
);
```

同步引擎**不直接持有 Database 或 Dio**，通过 DAO 和 ApiClient 间接访问，保持分层清晰。
